PyxeeBot.

A Discord music bot rewritten from the ground up in Rust — serenity, poise, songbird — and tuned, line by line, to run well on hardware that has no business running it well: a single shared vCPU.

The signal chain

What actually happens between a !play and the first sample of audio. Each stage runs, in this order, every time.

01 / search
Flat-playlist query

A lightweight yt-dlp search, no format resolution yet. Repeat queries hit a shared results cache instead of running twice.

02 / rank
Score every candidate

Title and uploader overlap, fuzzy matching, discouraged-token penalties, JP-original detection — up to 10 candidates, ranked in microseconds.

03 / resolve
Extract + connect, together

The winning track's stream is resolved while the bot joins your voice channel — concurrently, not back to back.

04 / play
Decode in-process

Symphonia decodes the stream directly. No ffmpeg anywhere on the box.

Engineered for one vCPU

Oracle Cloud's free tier gives you a fraction of a core. Most of this bot's design decisions trace back to that one constraint.

▲

Two separate concurrency limits — heavy per-video extraction is capped tight to avoid CPU contention; lighter search listings get their own, more generous budget.

▲

Background prefetch never blocks an urgent request — if you hit skip while the next track is quietly pre-resolving, your skip always wins the CPU.

▲

No ffmpeg dependency — audio is decoded in-process via Symphonia, one less subprocess spawned per track.

▲

Everything worth caching is cached — resolved stream URLs and raw search results both, TTL-bound and shared across every command that could reuse them.

MIT licensed. Deploys itself — push to main, GitHub Actions tests, builds, and restarts the service, with automatic rollback if it doesn't come back up clean.
